# rc.5 持续值守与环境刷新恢复

恢复工具修订：`rc5-recovery-20261029-patrol1`。本修订不修改桥收发协议及入站多媒体构建号，安装包须以新的 SHA256 核验；独立补充工具不等于升级了运行中的多媒体后台。

恢复分为桥服务恢复与 Muse 原生任务补位。Linux 脚本不能创建 Muse 原生任务。本方案由 Muse 主聊天的主代理登记平台巡检、维护 worker 台账，并在收到平台自动通知后负责查询和重建 worker；巡检负责检测与通知。必须验证通知能自动送达有权限的原主聊天，不能假定定时任务的独立运行就是原主聊天。未验证的平台入口不能算自动恢复。

## 正确的只读巡检

本修订的 hook 与定时巡检统一使用 `deploy/patrol.sh`。部署时登记已核验安装目录（或独立补充包）的真实绝对路径、Node 路径、config、JOB_DIR 和巡检状态目录；禁止再试裸 `muse-link`、猜测平台安装目录或在失败后退回旧 CLI。不为更新工具重启健康桥，也不把工具修订号当运行后台的 build。

```bash
# 首次只检查，不推进去重状态，不修复、不通知
bash "$HOME/.local/share/muse-link/current/deploy/patrol.sh" --check
# hook 与每 3 分钟巡检均使用这个记录入口；默认输出 JSON
bash "$HOME/.local/share/muse-link/current/deploy/patrol.sh"
```

可传 `--config`、`--job-dir`；独立工具包用其绝对路径。默认私密状态目录 `~/.local/state/muse-link-patrol`，两个入口必须一致，需自定义时设置相同的绝对 `MUSE_LINK_PATROL_STATE_DIR`。入口先核对目录是当前属主的真实规范路径，再收紧为 0700（含清除父目录继承的 setgid）；状态 0600，不修改父目录或他人目录。`--check` 也可创建锁并收紧专用目录权限，但不写巡检状态。同一 flock 覆盖观测、去重判定及保存，锁占用本轮输出 skipped、不当作健康，不能删除锁文件或状态来凑成功。入口不读取桥数据库，不领取、不发送、不补位。

JSON 的 `decision` 表示是否需要平台处理，`notification.notify_user` 才表示本轮是否应通知用户；`work` 是内部待办，不发健康长报告。健康轮次与完成回调一律静默；重复故障默认 60 分钟内不重报，故障类型变化和恢复另行通知。普通上游轮询错误需至少两次连续观测且相隔 10 秒确认；桥不可达、登录或存储故障立即记录。瞬时失败恢复时保存证据，不发未曾告警故障的恢复通知。存在收件/工具结果时内部 wake 最多每分钟一次；常驻 worker 自己持续 next，不依赖 wake 消费。

先读取一次并私密保存本轮报告，必要时按既有授权调用统一恢复入口，再复读报告。一次巡检只向用户合并发送最后状态，勿先发“来源未知”又补一条；若已恢复且恢复台账吻合，可一并说明由可信入口恢复。`decision=silent`、`notify_user=false` 或 `skipped` 的平台完成回调不得转成例行消息。平台若不能抑制自动完成通知须如实标缺项，不声称脚本已控制平台投递。输出 wake 不代表送达，`delivery_verified=false` 保留；稳定故障的小时提醒也不是补投成功证明。

新版 `deploy/wechat-hook.sh` 使用同一入口，可设置 `MUSE_LINK_PATROL` 为补充包内 `deploy/patrol.sh` 的绝对路径，另设实际 config/JOB_DIR。更新原 hook 注册与完成回调规则，先 dry_run；外层只适配一次平台协议，不能拼接两条 HATCH 结果。路径缺失或检查异常非零退出，不回退旧入口，也不伪造 silent 成功。检查器错误只输出固定脱敏码，原始 stderr 不转发微信。

`state.json` 有界保留最近观测、当前故障首个/最后证据和上一故障恢复证据；字段包括实际 HTTP/transport 错误码、health.problems、队列、工具、版本/build。系统证据包括 boot 标识的私密哈希、uptime、服务单元存在/变化和桥 since 变化；对外只给变化布尔值，不输出标识。boot 变化只证明观察到的启动标识变化；单元丢失、桥 since 重置、HOME 留存均不单独证明 Muse 环境刷新。权限不足或首次观测为 unknown；刷新原因需平台直接证据。

新版恢复入口持久化 `last_attempt` 的开始/完成、动作和结果，便于同一故障关联。旧入口没有该字段时记来源未核实，不靠时间窗猜谁执行了恢复。未部署新版工具、实际后台缺 build、原生补位及真实刷新未测分别列出，不能因版本号都是 rc.5 宣称升级完成。

从实际安装位置运行，所有消费者、hook 和巡检使用同一个后台工具目录：

```bash
node "$HOME/.local/share/muse-link/current/scripts/runtime-check.mjs" \
  --config "$HOME/.config/muse-link/config.json" \
  --job-dir "$HOME/.local/state/muse-link-worker/jobs"
```

该脚本只调用本地 status/health API、读取后台工具元数据；不打开桥 SQLite、不领取、不发送、不 ack。输出不含正文、token、账号、工具结果或私密路径。退出码 2 表示检查有故障或缺项，不能因此永久停止消费 backlog。缺失 build 不代表已装多媒体增强，应核对后台 build 与安装包；相同 version 不等于相同构建。

后台工具 `node scripts/tool-job.mjs list/pending --dir ...` 不获取桥数据库锁。若巡检报 state_locked，保留实际命令、退出码和脱敏错误，核对目录和入口，不能称作“桥运行时的正常现象”，也不能以队列为空代替检查成功。

报告中的 `worker.alive=null` 是刻意保留的边界。最近领取、租约续期、队列为空、health=true 都不是原生任务仍运行的证明。实际执行补位的主代理必须查询台账内真实 handle：

台账缺少完整 handle 时，由主代理先用原生工具核实并私密补全。按创建时间、父代理、平台数据库或任务目录推断身份只能辅助排查，不能替代该 handle 的原生查询。独立巡检的 direct 子任务列表为空，不能证明主聊天的 worker 已结束；巡检记 unknown 并经正式入口通知主聊天，不自行补位。主聊天收到后仍需原生核实；主聊天也无法确认时不创建替代者。独立巡检的查询范围受限，不等于主聊天也没有创建或查询权限。

- running、starting、等待授权：保留，不补位。任务变慢另行检查。
- 已明确终止且没有接班者：对账旧交接后补位。
- 查不到、查询失败、创建回执不明或存在多个可疑任务：unknown，先核对，不重复创建。

## 服务单元丢失

HOME 持久化而 /etc 被重置时，只重建服务单元，无需再安装依赖、init、扫码或复制数据库：

```bash
bash "$HOME/.local/share/muse-link/current/deploy/repair-service.sh" --check
# 巡检已具备授权、维护开关关闭且安装材料完整时：
bash "$HOME/.local/share/muse-link/current/deploy/repair-service.sh" --apply
```

脚本核对 rc.5 托管安装、HOME 属主、Node 24、systemd 与原私密配置/环境；渲染真实 HOME/用户/Node 路径。仅缺失时安装单元，已有不同单元或符号链接会保留并拒绝覆盖。apply 使用 OS 文件锁互斥；仅 daemon-reload，不启动、重启、enable 服务，不改 hook、配置、current、数据库或登录。check 会短暂创建并删除一个私密渲染文件，不写服务或业务状态。

有实际运行桥时继续复用。仅确认桥意外停止、没有其它实例、未处于主动维护，才通过下面的统一恢复入口启动；不要让巡检拆成多次独立命令。缺登录时仅通知扫码，不循环建码。不要重启活跃副作用来凑验收。

## 可直接使用的桥恢复入口

本安装包自带 `deploy/recover-service.sh`、`scripts/recover-service.mjs` 和 `src/service-recovery.mjs`，不需要从某个用户的私密环境复制脚本。先运行：

```bash
bash "$HOME/.local/share/muse-link/current/deploy/recover-service.sh" --check
```

新装时 `deploy/install.sh` 会在 `~/.config/muse-link/recovery.json` 创建 0600 的默认策略；已有文件保持不动。默认 `auto_start=false`、`maintenance=false`。只有用户已授权意外停止时自动恢复，才由主聊天将该私密文件的 `auto_start` 改为 `true`；主动维护前先将 `maintenance` 改为 `true`，维护结束后按用户意图恢复。策略修改也须取得同一把 recovery.lock，等待正在进行的恢复结束，再停服务，不能在锁外强停桥。旧安装没有该文件时，在确认不存在文件或符号链接后，从 `deploy/recovery-policy.example.json` 复制为 0600，再按已有授权设置；不要覆盖原策略。

已获恢复授权后，让原有每 3 分钟巡检调用同一个公开入口：

```bash
bash "$HOME/.local/share/muse-link/current/deploy/recover-service.sh" --apply
```

独立补充包可把上面入口替换为已核验补充包的绝对路径。它使用随包提供的 repair 脚本，核对 HOME 中原托管安装并读取原服务模板，不要求把新助手复制进旧 release，不切换 current、不替换运行中的桥。当前入口支持默认系统服务 `muse-link.service` 和默认配置路径；自定义部署应先适配并验证，不凭猜测替换路径。

外层 bash 在 `~/.local/state/muse-link-recovery/recovery.lock` 持有同一个 flock，直到策略复读、实际端口/进程/服务检查、repair、enable、仅一次非阻塞 start、最多约 45 秒健康复查和结果保存全部完成。不要删除或换锁文件，不直接调用内部 Node 入口。实例检查不明、有监听、服务正运行或正在启动时不再启动；活跃但不健康的桥交诊断处理。维护策略在修复和启动前复读。缺登录不会自动扫码，运行中的桥不会因 health=false 被重启。

状态保存在同目录的 0600 `state.json`。明确失败从 3 分钟开始指数退避，最多 30 分钟；结果未知或在启动过程中中断时保留 `pending=true`，下一轮不会盲目再启动。主聊天须只读核对实际服务与进程；桥健康时入口自行清除旧意图，否则记录人工核对结论后才能清除未决状态。不要为通过检查删状态。`--check` 不修复、不启动、不保存恢复状态；仅锁目录/锁文件可能创建。

退出码：0 健康或已恢复；1 前提/检查失败；2 锁占用；3 维护、未授权、现有/不明实例或未决意图；4 退避；5 单元修复失败；6 启动失败或健康未核实；10 只读检查发现需要恢复但未执行。JSON 只含状态，不输出账号、token 或原始命令日志。此入口只恢复桥，不能创建 Muse 原生任务，也不会注册平台巡检；后者仍由主聊天按正式工具执行。

## 平台巡检与唯一接班

先让主聊天登记的平台巡检实际定时触发，验证其通过正式的平台回调/投递入口自动到达原主聊天，再由该主聊天查询台账 handle。记录巡检注册、触发 UTC、投递结果、主聊天实际执行上下文及原生查询结果；平台支持何种入口以实际工具定义为准，不虚构参数或用未验证的 hook wake 代替已投递。

主聊天的查询/创建能力和巡检到主聊天的自动投递能力是两个检查项。独立巡检能创建并查询自己的短任务，只证明该次运行有这些权限，不能证明它能查询主聊天的 worker，也不能证明自动通知链路已接通。若平台没有正式投递入口或未实测送达，保留检测，明确自动通知/恢复未接入，不能要求用户每次转达后还记为自动成功。

只有另行选择并验证“巡检独立运行直接补位”的方案时，才要求该运行同时能查询原 worker 和创建接班者；普通无派生权限的子代理不能担任这种恢复调度者。

健康时无需补位不等于创建权限已验证。经授权的能力测试仅创建一个返回固定标记即结束的短原生任务，保存并查询其真实 handle；不读业务交接、不领取微信、不成为消费者。接口不可用或创建回执不明时不重复测试，保留未通过。手动调度测试与实际定时触发分别记录。

平台巡检默认每 3 分钟；已有每 15 分钟注册时更新原注册，不另建重复项，并回读间隔、启用状态与下一次触发。它只是计划，实际恢复还包含调度、桥轮询和任务启动耗时，不承诺最长 3 分钟。检查保持有界；上轮尚未结束时跳过或由平台串行排队，不能并发执行恢复。

补单元脚本自身的锁只保护单元修复，不覆盖后面的服务启动。调度入口还须在 HOME 内用同一 OS 文件锁覆盖“读维护开关、检查实例、补单元、再次检查、启动一次、复查、保存结果”的全过程，不能在启动前释放锁。维护开关必须在持锁后重读；活跃实例不重启，已有不同单元不覆盖。失败按同一故障持久化退避，不能每 3 分钟无条件重复启动；查询未知或锁被占用时不把它当作成功。桥恢复锁与原生任务补位意图分别核验，shell 文件锁不能代替平台原生状态查询。

主聊天收到故障通知或 worker 结束回调后，主动执行只读核实，不等用户再发“恢复”。先读取维护开关和台账，在互斥范围内保存稳定恢复意图、原 handle、slot、交接位置与创建状态。同一故障的巡检通知和任务结束回调须合并处理，避免两个入口各建一个消费者。未决创建先查询，不能换标识再 spawn；成功保存新 handle 并查询。15 分钟内最多 3 次明确失败后的创建尝试，失败退避。报告出现在主聊天、但主聊天没有自动执行查询，只证明通知展示，不证明接班链路已通。

接班者对账原领取文件、完整 token、started 步骤、后台工具和发送 request。通过正常 renew 验证原 token；丢失/无效则等待合法重新领取。不抄数据库 token、不清有效租约、不重放 accepted、不凭空结清不明外部操作。

worker 完成一条即继续 next，空队列继续长轮询。阶段记录只写私密文件；不能为交报告提交终结任务。平台要求终止或上下文逼近边界时，保存交接，由有权限的调度者在确认旧任务结束后接班；不自行创建无权限的替代者。平台报告完成就是已结束，不能沿用其旧心跳声称常驻。

## 长任务与服务启动方式

桥故障恢复不能解决单 worker 同步等待工具的问题。按 [BURST_MESSAGES.md](BURST_MESSAGES.md) 后台启动工具后立即继续 next；有待完成工具、附件或发送时，每次 next 的 wait 不超过 5 秒，逐轮核对结果与续租；没有待办时再恢复 30 秒长轮询。当前 worker 必须实际回认新指令并留下工具未完成时继续领取的证据；只修改持久化提示文件不等于当前任务已生效。后台工具隔离不等于独立 Muse 任务并行，唯一任务被原生授权暂停时仍应如实说明限制。

用户级 systemd 作为候选只读核对：user manager、用户 D-Bus、linger、用户服务依赖及平台刷新后的启动入口必须分别验证。单元放在 `~/.config/systemd/user/` 只说明文件可以随 HOME 保留，不证明用户管理器会启动；linger 状态也可能在 HOME 之外被重置。未经验证不切换当前健康系统服务、不启用第二套桥实例。HOME 中有修复脚本不代表刷新后会有人执行；记录平台触发入口是否仍存在及实际执行结果。此前 HOME 留存的观察不能替代私密备份，也不保证账号永久重置后仍保留。

## 通知与验收

健康巡检只写私密记录，主聊天不逐轮汇报。仅故障首次出现、故障发生实质变化、恢复或需要用户操作时通知。同一故障用稳定标识去重，恢复后清除；不通过丢弃错误输出来“静默”。

分别记录：只读健康路径、巡检到主聊天的自动投递、服务单元缺失修复、原生 worker 补位、环境刷新恢复、等待授权不重复补位、主动维护不补位、创建回执不明不重建。受控破坏/刷新验收须另选用户认可的窗口；未测标未执行。用户手动输入恢复指令的接班不能算自动通过；主代理经真实平台自动通知后执行恢复，不能仅因执行者在主聊天就归类为“人工”，应依据实际触发与操作记录判断。

完成恢复后核验新 handle 在相隔至少一个 30 秒空闲 wait 的两次查询中仍运行且领取活动前进。真实微信验证由用户发送并确认手机收到；accepted 只说明接口接受。不得为测速伪造微信消息、回复或手机确认。持续值守证据不足时，不宣布生产级。
