# 用微信验证生产候选版

项目：https://github.com/xianjia95-oss/muse-wechat-clawbot

先做短时真实链路验收，通过后再做72小时观测。下面是测试步骤与通过条件，不是已完成的验收结果。Muse先准备记录，用户测试期间只操作微信；需要人工进入Muse或手动派发才能回复，应记失败及介入时刻。

当前交付必须为原生并行：自动领取后立即派发并继续领取，执行者完成即直接回复。仅十条最终都有回复不够；须有真实原生任务时间记录证明短任务在先到的长任务完成前已开始且先回复。单模型加后台工具、手工派发或静默回退串行均不能替代该项通过。

## 先让Muse准备

将 [完整验收指令](给Muse生产验收的指令.txt) 交给Muse。核对实际后台版本、hook真实注册和平台投递目标，运行 status、health、diagnose、metrics，保存脱敏基线。保留当前值守，不先停止worker，不重新扫码、不清租约；队列或未决工具有异常时先核对。

每条测试记录：测试编号、event_id、hook invocation及投递/运行关联、真实任务handle或主会话运行标识、入库/领取/执行开始/结果就绪/提交/accepted时刻、手机是否收到、有无人工介入。统一时间基准，不能拿EDT目录时刻直接和UTC日志比较。没有原始领取时刻就标不可获取，不用lease_until倒推。

请分别核对 rc.7 候选源码和实际运行的后台版本；拉取源码不会自动升级后台或配置平台 hook。worker_claim_gap默认60秒无成功领取进展的告警仅在对应后台生效；旧版本缺字段不代表通过或失败，仍以实际日志和手机为准。

## 短时测试顺序

| 步骤 | 用户怎么做 | 通过条件 |
| --- | --- | --- |
| 1. 常驻自动回复 | 准备完成后不再操作Muse主聊天，从微信发 `A01：只回复A01` | 无人手动派发，实际自动领取、回复，手机收到A01；保留完整关联证据 |
| 2. 连发十条 | 一分钟内分别发十条独立消息，编号A11到A20，每条要求只回复自己的编号；不能合成一条发送 | 十条全部有对应最终回复，缺失0、重复0、错配0，无人工介入；记录每条耗时，回复不要求按发送顺序 |
| 3. 长任务不挡短任务 | 发下面的L01，手机收到“L01开始”后连续发S01、S02、S03 | 至少一条短任务实际在L01完成前开始并回复，其余均有结果；L01最终完成，编号不串；证据包含真实原生任务运行 |
| 4. 自动冷启动 | Muse按下节准备好受控窗口后，用户只从微信发 `C01：只回复C01` | 无主聊天人工操作，hook实际触发运行并自动领取/回复；领取观察线60秒，超线先记失败 |
| 5. 轮换和故障恢复 | Muse按真实交接流程轮换调度者，用户再发 `R01：只回复R01`；另做一项无副作用工具超时测试 | 新调度者自动工作，旧子任务不重派，R01有回复；单项工具失败不挡其他任务，不重复执行外部动作 |
| 6. 媒体回传 | 要求Muse回传一张小PNG和一段短MP4，用户在手机打开/播放 | 图片可打开、视频可播放，有原请求回执；上传期间短文字仍可回复 |

L01可直接发：

> L01：请先回复“L01开始”，用独立任务执行90秒无副作用等待，结束后回复“L01完成”。期间继续自动处理其他微信消息。

L01开始是用户在该测试中明确要求的标记，仅用于确认重叠窗口，不作为业务占位模板；正常微信任务不自动发送开始确认。该标记使用稳定进度回复ID，结束使用原事件最终回复，不能拆成两个重复执行者；本测试预期两条对应回复。S01/S02/S03分别要求只回复各自编号。观察线60秒衡量自动领取，不代表模型最终回复必须60秒内完成；每条提交和手机耗时单列。若长任务未开始或已提前结束，不能据该次结果断言并发成功，须注明并重做有效重叠测试。

外部API失败验收按[任务隔离与重试规则](EXTERNAL_API_TASKS.md)：只用本地无副作用模拟端点，记录尝试次数和整段截止。失败任务进行时，其他编号短任务仍自动开始并先回复；到截止后原任务停止尝试并给出真实失败/结果待核对反馈，不因换班或换工具重置预算。无需真实外部API凭据，也不调用真实生图服务。

## 冷启动与恢复由Muse安全准备

普通轮换按 [自动唤醒与交接](AUTOMATIC_DISPATCH.md) 保留旧者，先验证主级接班者的真实派生/查询权限并保持待命，不能用普通子代理充当调度者，再暂停旧者next并交接激活，确认新者实际工作后才结束旧者。

冷启动测试单独安排：确认没有未完成测试、未知发送、未决工具副作用或不明所有者；仅让调度者正常结束，保留微信桥和已启用的真实hook，预先保存恢复方式和独立记录路径。用户只在微信发C01，测试期间不向Muse发消息帮它启动。超过观察线或必须人工恢复就记失败；保存故障时证据后按实际任务状态恢复唯一值守。手动恢复成功不能回填为自动通过。不杀正在处理任务的worker，不凭缺目录自动重派，不改数据库token。

wake输出或outcome=wake不足以证明平台投递；还需任务实际运行及成功领取。原生任务未自动创建/恢复时须先修该链路，不能只保留常驻worker就宣称冷启动通过。

还须在一次正常平台刷新后，或平台支持且没有未决副作用的受控窗口，验证 [运行环境恢复](RUNTIME_RECOVERY.md)：确认全部旧进程/任务终止，恢复唯一服务与具备派生权限的主代理调度，正确接续原交接，微信新消息无需人工进入主聊天即可回复。保留刷新时间、自动恢复入口、实际领取和手机时间。缺原始token等待有效租约到期不是自动恢复完成；不得为通过测试清租约或重派未核实外部操作。不要强制刷新正在执行用户业务的环境。

## 故障、备份与持续验收

前面的短时项目通过后，按PRODUCTION.md在无危险副作用的维护窗口做真实服务重启、短暂断网、旧租约拒绝、重复原请求去重和失败恢复。unknown不盲目重发，started须核对，不能用新ID把失败“测成成功”。

暂停hook并停止服务后备份；在隔离状态目录校验和恢复，不连接同一账号启动第二个接收进程，不覆盖在线状态。确认恢复闸门、原状态保留及实际恢复时间；维护结束恢复唯一服务和值守并用微信复验。没有实际执行的项目填“未执行”。

全部短时验收通过后，Muse用真实后台管理运行只读观测器72小时，期间持续有代表性的文字、长任务和媒体。报告私密保存，不上传正文/token、数据库或本地服务器压力资料。记录资源和磁盘趋势、意外重启、任务历史容量及失败处置；不新增内存压力测试。观测器本身不会执行任务或证明手机收到，须合并真实消息记录。

从候选源码目录运行，显式使用同一配置路径：

```bash
node scripts/observe.mjs --config "$HOME/.config/muse-link/config.json" \
  --duration 72h --interval 30s --report "$HOME/private-reports/muse-link-72h.json"
```

要核对真实进程确已持续运行，不能只报告“已启动”。completed=true、实际时长达到72小时且无未解决故障，结合人工收取记录才可评估通过。中断、unhealthy或缺项应如实记录，修复后对受影响项目重新验收，不能只截取最后一次healthy。

平台刷新导致观察器退出时，保留旧报告，用新的UTC时间戳路径启动新段，记录缺口和恢复时间。若要求单段连续72小时，分段不能算通过；若另定跨刷新服务可用性标准，须明确标准并保留整个72小时的中断/恢复证据，不能把分段时长相加伪装成无中断。

## 交付结果

每项填写“通过 / 失败 / 未执行”，附脱敏证据位置、人工介入情况和未解决问题。自动触发、十条连发、长短任务重叠、轮换恢复、媒体、故障及备份恢复、72小时持续观测缺一项，就不把该部署标为生产验收完成。

当前媒体测试仅验证Muse本地文件发回微信；微信入站图片、视频和文件下载/识别仍不支持，不能据回传成功宣称媒体全部双向支持。
