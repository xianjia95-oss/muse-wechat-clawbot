# Muse 原生并行处理微信任务

Muse 当前环境已反馈能够同时派发多个独立任务。微信值守只有一个轮换 worker 是当前部署方式，不是桥或 Muse 原生任务能力的并发上限。优先使用本流程；[后台工具队列](BURST_MESSAGES.md) 仍用于工具资源控制或缺少原生并行能力的保底部署。

## 执行方式

保留一个轻量值守调度者：接收事件、判断上下文依赖、保存私密交接并派发。不要在调度循环里执行长推理、等待子任务完成、等媒体上传或处理长 shell/API 测试。独立消息收到后立即派给 Muse 的原生任务，各子任务完成后直接调用原事件的 muse reply 回微信。调度者无需等结果再转发，因此短任务不用等先收到的长任务。

本仓库没有 Muse 原生任务 API 的凭据或工具入口；派发必须使用当前 Muse 环境真实可用的并行任务工具，并记录实际 task handle/ID。不能用 Node 子进程、后台 shell 或 Promise.all 冒充多个 Muse 任务。桥已支持各事件的独立租约，不需要关闭 token 校验或修改 --limit 1；后者仅表示一次领取一条。

## 调度与交接

1. 按 MUSE.md 用新的 0700 目录执行 `muse next --limit 1 --lease 30m --output '<新私密目录>/task.json'`。这个文件包含 token 和正文，只在同一受信运行环境内交接，不贴进用户聊天、公共任务标题或日志。
2. 将 event_id、原完成 request_id、私密 task.json 路径、稳定派发标识和当前所有者写入私密交接记录，先标记 dispatching。每个事件最多一个实际执行者；独立事件使用不同目录，不共用可变的“当前任务/token”文件或全局变量。
3. 使用真实 Muse 原生工具创建子任务，只传该事件的私密文件位置、必要上下文及本页执行协议。创建成功持久化真实 task handle，将执行权交给该子任务；调度者继续领取，不等待它思考、运行工具或最终回复。子任务接管前由调度者维持该事件正常续租，接管确认后由子任务负责。
4. 创建失败须保留原事件和有效租约，记录失败原因、正常续租并恢复派发。创建结果不确定或调度者崩溃时，先按稳定标识查询真实原生任务及交接；不能因没收到创建回执就再启动一个。没有可核实的任务 ID 时保留待核对，不自动重派或清租约。
5. 接班仅替换值守调度者；按 [自动唤醒与交接](AUTOMATIC_DISPATCH.md) 先创建不领取的待命新者、确认真实 handle，再令旧者暂停 next 并交接激活；新者实际领取/派发成功后才结束旧者。不能先停旧者再依赖未验证的 wake，也不能两者同时消费同一事件。核对已派发的真实 task handle，仍运行的子任务继续负责原事件，不因调度者换班而取消、再领取或重复执行。执行者换班才按 MUSE.md 的同一事件接管规则，核对原执行者/工具已停止和原始交接，再通过正常 renew 接续。
6. “接着刚才的”“取消”“改成另一种”、共享文件修改、部署等有依赖的消息，由调度者关联原任务并协调；不要盲目拆成独立修改。同一聊天里的无依赖请求可并行，不必为保持整个聊天 FIFO 等待前一条完成。

领取后、子任务接管前先 progress 不是强制要求；需要时使用稳定 reply-id，并可 --async 保存回执后继续派发，避免连进度发送都挡住调度。告警与空事件按原协议处置，不无谓创建子任务。调度者不在自己这里执行复杂短问答，否则仍可能挡住后续派发。

## 每个原生子任务的约定

- 只处理传入 task.json 中的那一个事件，不再 next、不消费其他事件；不使用其他子任务的 lease_token。读取 completion、execution，遇 unknown/rejected 或未决 started 先核对，不重做外部动作。
- 按原协议每 5 分钟 renew 到 30 分钟，将返回的 lease_until 写到本事件的独立私密进度文件。长工具阻塞时仍需可用的续租路径；无法维持续租时停止新操作并报告，不能靠 30 分钟租约无限等待。原始领取文件保留，不覆盖其他事件文件。
- 原本需要 checkpoint 的工具仍先 started，结果核实后 completed。多事件可同时各有自己的 started；同一个事件不因此获准重复执行。目标系统有副作用的操作继续使用自己的幂等键及原有授权。
- 结果准备好立即用本事件 token 调用 `muse reply`，由桥自动路由并生成稳定 request_id，accepted 后自动 ack。子任务直接发送，不等调度者收齐全部结果，也不等待其他更早的任务。独立结果可以按完成顺序回传；较晚回传的长任务用自然语言指明对应原请求。
- 媒体可用 --async，保存原正文、文件路径和回执，按 request 状态及租约继续跟进，accepted 以前任务仍未完成。202/pending 不代表微信已收到；unknown 不自动重发。子任务只有已回传或明确持久化未决处置后才能结束。

桥会保护不同事件的 token 隔离及稳定请求去重；同一 token 被错误交给两个执行者不等于获得两个合法执行权。创建/接管的唯一性仍须在原生任务记录和私密交接中核实；租约不能撤销已经发生的外部动作。

## 机器资源与工具队列

这台两核机器限制的是本地计算吞吐，不要求把所有原生任务都串行。网络等待和远端推理可重叠，本地计算密集工具先保持一个活动任务。rc.6 的 tool-job 配置仅约束交给它的可信脚本，不是 Muse 原生任务总数，也不能限制绕过 helper 执行的 shell。

这一轮 10 条独立轻任务验收不要额外套用原来的“四个 Muse 任务”上限。实际并发按 CPU/RSS、上游限流和平台任务状态控制；达到资源阈值时明确记录等待原因、保持事件续租，恢复后再派发。不能把“平台没有硬数量限制”当作机器没有资源上限。

确有 10 个网络脚本需同时等待时，可显式将同一个私密 helper 根目录配置为 `--max-active 10 --max-io 10 --max-cpu 1 --max-queued 64`，仍执行原启动期限、renew/refresh 和去重协议。所有子任务共用该工具调度根目录及策略，每个工具用不同稳定 job ID；不要各建一套队列绕过 CPU 上限。原生模型任务数量不由这一命令设置。

## 真实验收

先用无副作用任务验收：调度一个需等待 20 秒的原生子任务，期间派发其他简短任务并立即回复；保存真实原生 task handle、event_id、开始/结果就绪/提交/accepted 时刻。要求其他任务在第一个结束前已经开始并回传，不只是记录“计划派发”。然后从手机一分钟内连发 10 条有编号的独立消息，逐条核对微信回复、原生任务归属和事件。

再验证：一个子任务超时不挡住其他任务；调度者接班不重复派发；串用 token 被拒；旧执行者无法用失效租约续租/发送；同 ID 重复提交不重复发；相关追问或取消准确作用于原任务。回传脱敏事实，不回传 token、正文、完整私密文件或 API 凭据。

本地 HTTP 并发测试仅验证桥的行为，不能证明原生创建/接管已经接入，更不能证明手机收到。真实 Muse task handle、并行开始记录、手机结果与生产持续验收仍需由部署环境提供。
