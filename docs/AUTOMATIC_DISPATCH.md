# 常驻池维护、自动唤醒与交接

日常消息由多个常驻 Muse worker 直接 long-poll、原子领取和回复，不逐条依赖 hook→主代理→spawn。主代理创建/维护池；桥不含 Muse 原生创建 API。hook 的 wake 只证明检测，不能证明池补位或刷新恢复已运行。

## 排查原则

排查时分别确认消息入库、hook 检测、平台投递、实际领取和独立任务执行。检测器的 wake 只说明检测结果，不证明平台已经投递；旧值守停止前必须验证替代入口。实际 invocation、任务 handle 和现场时间线仅保存于部署环境的私密记录。

证据支持“入库到自动消费链路未完成”，尚不能证明平台 bug。还需核对投递目标、去重/合并、主会话是否进入新一轮及调度者是否执行 next。agents 目录没有新增子任务只是旁证：平台也可能唤醒已有任务或主会话。统一使用 UTC 对应 invocation 与任务，不能按目录时间猜关联。

## 核对 hook 与投递

1. 保留当前值守者，不重启健康桥、不重新扫码、不清库。只读核对实际启用 hook 的标识、目标任务/会话、触发指令、权限、间隔和投递/去重策略；注册成功不等于投递成功。
2. 对一次真实 invocation，核对退出码、stdout 是否恰好一个结果、解析后的 outcome，再追踪触发入队/投递的接受、失败或合并状态。使用平台真实查询入口，不发明字段值或 API。
3. 当前部署报告格式为 `HATCH_HOOK_RESULT:{"decision":"wake","reason":"..."}` 或 silent。一次调用只能选择一种结果，不能连续输出 wake 和 silent；调试信息放 stderr，不泄露正文/token。rc.7 检测器默认 plain，可显式 MUSE_LINK_HOOK_FORMAT=hatch 输出单行 JSON；外层已经 _hatch_hook_emit 适配时保持 plain，不双重包装。安装升级/回滚保留自定义平台 hook，已有包装仍须合并新检测逻辑并 dry_run；保留适配不代表已应用新探针。
4. 若唤醒已有主会话，检查实际 turn/运行记录及权限，不只寻找 agents 新目录。记录真实 task handle 或主会话运行标识、运行开始及成功 next 时刻。投递若合并到已结束任务或错误会话，修正注册；若被繁忙任务阻塞，将池维护与长任务分开。
5. 没有平台投递凭据时标为“投递未验证”，保留 invocation ID 供平台检查。常驻值守者恢复消费，不等于 hook 冷启动已修好。

## 检测、常驻消费与池维护分开

周期检测脚本和诊断探针只读 status/health/必要的 diagnose，输出单个 wake/silent，不 next、不清 claim。真实常驻 Muse worker 按 [NATIVE_PARALLEL.md](NATIVE_PARALLEL.md) 自己直接 next/reply；子代理无需派生。探针不能成为唯一运行角色，主代理也不再为每条消息领取派发。

有 ready 但没人领取时，先核对实际池 handle、slot 和 next 记录，恢复可运行消费者。不能把 health 成功才 next 作为全池条件：backlog/claim_gap 正需要恢复消费；仍保留登录、恢复审查、资源闸门和租约保护。ready=0、leased>0 可能是正常工作。

一个任务等网络/授权时，其他空闲池员继续领取；全池被占仍排队。按入库、领取、开始、提交、accepted 分段定位，不能以“并行已启用”推断永不等待。常驻池不能自动批准权限，也不内置独立授权反馈路径。

## 切换与 slot 轮换

1. 保留现有消费者与事件所有者，主代理先核对真实任务及未完成交接，确认创建/查询能力。
2. 将真实原生常驻池补齐到目标 6 个，各用独占私密目录。已有健康 slot 保留，只新增缺失者；已有 3 个时只加 3 个，不重建整池。创建结果不明先查实际任务，不重复补位。它们可以同时原子领取不同新事件，不需要全局唯一 next 锁。
3. 确认新池真实运行并成功领取/回复无副作用测试事件后，才结束旧的每条派发职责。原已领取事件继续由原所有者处理。
4. 逐 slot 换班先确认新常驻者，再让旧者停新 next、完成或安全交接持有事件后退出；不先停全池。接管同一事件前确认旧执行者/工具停止，沿用原交接、完整 token 和正常 renew。

详见 [完整恢复指令](给Muse恢复常驻worker的指令.txt)。停止/创建任务跨越平台 API，不是数据库原子事务；多个消费者可重叠，但同一事件不能双执行。

## 连续消费、补位与冷启动分开验收

先启动池，主聊天不再人工操作，从微信分两批发独立消息，验证同一组常驻 handle 持续领取；一分钟连发10条、长任务期间短任务先回复另验。正常消费不要求每条都创建新任务，也不要求每条有 hook 投递记录。

再在无未决副作用的受控窗口验证单 slot 轮换/补位，保留其他池员。全池冷启动须独立安排恢复方式，不能为测试杀正在工作的人；主聊天无人操作，仅从微信发编号消息，记录入库→真实启动入口→池 handle→领取→accepted→手机。60秒无自动领取记失败并保留证据，手动恢复不算自动通过。

真实独立平台定时任务或刷新后启动入口若可用，可触达有派生权限的主代理，查询池状态并核对后补位。常驻执行者自己无需派生；池全灭后仅用失效的同一 hook 发更多 wake 不构成可靠看门狗。没有真实入口明确报告“自动恢复未接入”，后台 shell/观察器不能冒充 Muse 模型。

刷新可能杀死全部进程与任务，保留文件不证明存活；按 [运行环境恢复](RUNTIME_RECOVERY.md) 恢复唯一桥、对账并重建池。常驻消费通过、hook投递通过、刷新自动恢复通过分别记录，不能互相替代。

## 告警要保留具体事实

`worker_lease_stalled` 表示租约活动超过配置阈值，默认 600 秒。轮询仍正常时也可能出现该告警；它不等于微信网络故障，不证明任务已经死亡。缺原始样本的告警应记原因未核实。

ready=0且leased>0本身不是异常，正常执行中的任务也符合。只有健康/诊断返回具体停滞代码，或实际活动年龄达到配置阈值时，才按worker_lease_stalled核查。退出码能说明CLI调用成败，不能单凭它或“有租约”推断具体故障；保持具体代码和受控证据，不原样保存可能含凭据的stderr。

rc.7 新检测器对子进程设超时，失败复查一次；告警按具体代码节流，不阻挡 ready/工具结果 wake。告警时将受控字段保存到私密 ~/.cache/muse-link/hook-alert-state.json，包含时间、代码、轮询状态和队列计数，不包含凭据或正文。旧 hook 全丢弃 health 输出的记录无法补造；该缓存也不能证明平台投递成功。遇 worker_lease_stalled 应核对所有者/任务与正常续租，不清租约、不无限后台续租掩盖死亡、不无故重启健康桥。

告警 reason 包含 UTC 检测时间。平台每次收到 wake 后先读取当前 status/health，必要时 diagnose；旧告警延迟到达且当前已健康、无待办时静默结清，不按旧内容重启或重复通知。调用产生时间与另一 worker 启动时间相近不足以证明对应，必须用 invocation → 实际投递/turn → task handle 建立关联；统一 UTC 后再计算投递耗时。缺关联的数小时样本仅作排查线索。

## 桥侧证据

本地 rc.6 候选的 health/diagnose 增加 consumer：ready 消息默认 60 秒没有成功领取进展时，health 返回 503 且 problems 含 worker_claim_gap；operations.worker_claim_warn_ms 可调整，旧配置采用 60000。原有 5 分钟 backlog 告警、租约活动检查及 unknown 保护不变。

ready_wait_ms、without_claim_progress_ms 只说明桥观察到的领取进展。空 next 请求不算成功领取；近期成功领取重新计算观察期。worker_liveness_verified 和 platform_dispatch_verified 始终 false，不据此宣布进程死亡或平台故障。全部已领取但未回复由租约/步骤/发送阶段检查处理。

计数自桥启动起有效，启动前或离线领取未必可见。候选 scripts/diagnose.mjs 对旧桥也能只读分析已有 worker/queue 计数；缺遥测则报告 telemetry_unavailable。新的 readiness 告警需后台实际升级后生效。观察器能记录告警，不能启动 Muse；同一唤醒路径失效时，靠它投递告警也可能无人处理。
