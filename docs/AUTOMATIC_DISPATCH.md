# 自动唤醒与调度者交接

桥持久化消息、检测器输出 wake、平台投递、Muse 调度者运行、领取派发、子任务回复，是不同环节。桥不包含 Muse 原生创建任务的接口。打印 wake、invocation 的 outcome=wake、health 通过、手动派发后回复成功，都不能单独证明自动派发可用。

## 当前真实发现

排查消息入库、hook 检测、平台投递、主级运行、实际领取及独立执行各阶段；wake 本身不证明消费者已运行。现场标识与时间线只保存在部署环境的私密记录中。

证据支持“入库到自动消费链路未完成”，尚不能证明平台 bug。还需核对投递目标、去重/合并、主会话是否进入新一轮及调度者是否执行 next。agents 目录没有新增子任务只是旁证：平台也可能唤醒已有任务或主会话。统一使用 UTC 对应 invocation 与任务，不能按目录时间猜关联。

## 核对 hook 与投递

1. 保留当前值守者，不重启健康桥、不重新扫码、不清库。只读核对实际启用 hook 的标识、目标任务/会话、触发指令、权限、间隔和投递/去重策略；注册成功不等于投递成功。
2. 对一次真实 invocation，核对退出码、stdout 是否恰好一个结果、解析后的 outcome，再追踪触发入队/投递的接受、失败或合并状态。使用平台真实查询入口，不发明字段值或 API。
3. 当前部署报告格式为 `HATCH_HOOK_RESULT:{"decision":"wake","reason":"..."}` 或 silent。一次调用只能选择一种结果，不能连续输出 wake 和 silent；调试信息放 stderr，不泄露正文/token。rc.7 检测器默认 plain，可显式 MUSE_LINK_HOOK_FORMAT=hatch 输出单行 JSON；外层已经 _hatch_hook_emit 适配时保持 plain，不双重包装。安装升级/回滚保留自定义平台 hook，已有包装仍须合并新检测逻辑并 dry_run；保留适配不代表已应用新探针。
4. 若唤醒已有主会话，检查实际 turn/运行记录及权限，不只寻找 agents 新目录。记录真实 task handle 或主会话运行标识、运行开始及成功 next 时刻。投递若合并到已结束任务或错误会话，修正注册；若被繁忙任务阻塞，改为独立轻量调度者。
5. 没有平台投递凭据时标为“投递未验证”，保留 invocation ID 供平台检查。常驻值守者恢复消费，不等于 hook 冷启动已修好。

## 只读检测与主级处理必须分开

只读限制适用于周期检测脚本及诊断探针：读status/health/必要的diagnose并输出一个wake/silent，不next、不派生、不清理claim。它不能成为唯一的消息消费者。

平台收到wake后，实际具备派生权限的主级处理入口必须读取当前状态：有ready事件就执行`next → 私密交接 → 创建独立原生执行者 → 继续next`，已派发事件按台账核对，不重复派发。只有当前无ready、无待处理回执/结果且无需处置的问题时，才静默结束。healthy只代表就绪检查通过，不能据此跳过ready事件。

如果“hook任务提示语”被配置为只读并禁止next/派生，而它又是wake之后唯一会运行的任务，则自动消费链路仍未接通。若平台只能先唤醒诊断子任务，该子任务不能自行冒充主级调度；须有经验证的后续主级运行入口。delivery.surface=main是配置证据，不能单独证明该入口实际执行，仍需一次自动运行里的next与spawn真实工具记录。

旧值守结束后，先核对私密台账和真实原生任务，再接管 ready 消息；人工恢复不计自动验收通过。

## 切换时先准备新值守

停止/创建原生任务跨越平台 API，不是桥数据库内的原子事务。采用准备、交接、确认流程，不先结束旧者再依赖未经验证的 wake：

1. A 继续服务。B 必须是真实具备派生权限的主级会话，而非主代理刚创建的普通子任务。先用无副作用任务验证 B 实际创建/查询能力，再保持待命，不 next、不接管业务事件。当前平台只有主代理具备该能力：从串行子代理迁移时，B 就是现有主代理；没有独立主级会话入口时不声称能创建另一个主级 B。
2. A 暂停新的 next，持久化待派发事件、正在创建的派发及真实子任务 handle；已有子任务继续。确认 A 不再领取，但暂时保留 A 为可恢复待命者。
3. 通过平台真实任务通信激活 B 并确认。B 核对交接及实际执行者后开始 next。创建/激活结果未知先查询，不重复创建，也不同时恢复 A。不能以杀进程/删记录冒充交接。
4. B 实际成功领取并派发一条新的无副作用测试事件后，才结束 A。B 明确失败时，先确认其没有领取/派发，再恢复 A。可以同时保留两个原生角色，但只有一个活动领取者；多个独立子任务继续并行。
5. 不因调度者换班接管仍运行的子任务。同一事件恢复须使用原交接和正常 renew；unknown、started 未决或创建结果未知先核对，不清租约、不换 ID 重跑。

## 自动启动与恢复验收

先保持现有值守验证连续消息，再在无未决副作用的受控窗口测试：

- 仅让调度者正常结束，保留桥和真实 hook；已派发事件仍有明确所有者。
- 用户只从微信发编号无副作用消息，Muse 主聊天保持无人工操作。记录入库 → invocation → 实际平台投递/主会话 turn 或任务 handle → 成功领取 → 子任务 → accepted → 手机收到。
- 本次以自动领取 60 秒为观察线，不承诺秒级 SLA。超线记失败、保留队列证据，再按交接规则恢复已知值守；手动恢复不能回填为自动通过。
- 重复正常轮换，验证长任务运行期间短消息仍自动派发/回复。冷启动和换班都自动通过后才结束临时兜底。

若平台真实提供独立定时原生任务或服务管理入口，可让它核对实际调度者 handle/状态，确认旧者停止后恢复唯一值守，并保存创建/查询记录。它必须独立于当前失效的 hook 投递路径；反复发送同一种 wake 不构成独立兜底。没有真实入口则报告“自动恢复未接入”，不能用 shell 常驻循环冒充 Muse 模型。看门狗不得消费事件、取数据库 token 强抢或自动重放副作用。

若刷新终止进程和原生任务，即使磁盘文件仍在，也须核对原任务与交接，恢复唯一服务和具备派生权限的主级入口。

## 告警要保留具体事实

worker_lease_stalled 按租约活动年龄和配置阈值核查，不等于微信网络故障，也不证明执行者已死亡。缺原始证据时记原因未核实。

ready=0且leased>0本身不是异常，正常执行中的任务也符合。只有健康/诊断返回具体停滞代码，或实际活动年龄达到配置阈值时，才按worker_lease_stalled核查。退出码能说明CLI调用成败，不能单凭它或“有租约”推断具体故障；保持具体代码和受控证据，不原样保存可能含凭据的stderr。

rc.7 新检测器对子进程设超时，失败复查一次；告警按具体代码节流，不阻挡 ready/工具结果 wake。告警时将受控字段保存到私密 ~/.cache/muse-link/hook-alert-state.json，包含时间、代码、轮询状态和队列计数，不包含凭据或正文。旧 hook 全丢弃 health 输出的记录无法补造；该缓存也不能证明平台投递成功。遇 worker_lease_stalled 应核对所有者/任务与正常续租，不清租约、不无限后台续租掩盖死亡、不无故重启健康桥。

告警 reason 包含 UTC 检测时间。平台每次收到 wake 后先读取当前 status/health，必要时 diagnose；旧告警延迟到达且当前已健康、无待办时静默结清，不按旧内容重启或重复通知。调用产生时间与另一 worker 启动时间相近不足以证明对应，必须用 invocation → 实际投递/turn → task handle 建立关联；统一 UTC 后再计算投递耗时。缺关联的数小时样本仅作排查线索。

## 桥侧证据

本地 rc.6 候选的 health/diagnose 增加 consumer：ready 消息默认 60 秒没有成功领取进展时，health 返回 503 且 problems 含 worker_claim_gap；operations.worker_claim_warn_ms 可调整，旧配置采用 60000。原有 5 分钟 backlog 告警、租约活动检查及 unknown 保护不变。

ready_wait_ms、without_claim_progress_ms 只说明桥观察到的领取进展。空 next 请求不算成功领取；近期成功领取重新计算观察期。worker_liveness_verified 和 platform_dispatch_verified 始终 false，不据此宣布进程死亡或平台故障。全部已领取但未回复由租约/步骤/发送阶段检查处理。

计数自桥启动起有效，启动前或离线领取未必可见。候选 scripts/diagnose.mjs 对旧桥也能只读分析已有 worker/queue 计数；缺遥测则报告 telemetry_unavailable。新的 readiness 告警需后台实际升级后生效。观察器能记录告警，不能启动 Muse；同一唤醒路径失效时，靠它投递告警也可能无人处理。
