# 主代理值守与环境刷新恢复

项目：https://github.com/xianjia95-oss/muse-wechat-clawbot

## 已确认的部署约束

部署前核实主级创建/查询权限、子代理派生权限及刷新后的状态保留范围。残留任务目录不证明任务仍然运行。

因此应由有派生权限的主代理承担轻量调度，子任务只执行自己的事件；一个常驻子代理不能自动成为并行调度者。刷新后旧任务文件不代表存活，systemd 单元、cron、常驻 shell 和本地观察器也不能保证跨整个环境刷新存活。独立启动入口必须在平台刷新后仍可运行，并能触达主级会话；本仓库没有该平台 API，不能仅靠安装桥就完成它。

## 首次改成主代理调度

1. 保留现有串行兜底，主代理先用真实工具创建、查询并完成一个无副作用子任务，记录真实 handle；不是让子代理承诺“之后转告”。
2. 准备私密持久化交接，至少包含 event_id、原始 handoff_file、稳定回复/步骤编号、原生任务 handle、当前所有者及接管状态。不要把 token 写入公共任务标题、报告或日志。
3. 命令旧串行者暂停新的 next，确认暂停，保留它已领取事件的所有权和续租。主代理核对后领取新事件，立即派发独立子任务，不等待结果。已领取事件不重复派发；若转移它，先确认原执行者及工具已停止，再按原记录交接。
4. 主代理实际自动处理一条测试消息后，再结束兜底的新消息消费职责；已有原任务按交接处置。不能先停旧者再等待未经验证的 wake。
5. hook 的实际投递目标必须是能执行该调度协议的主级会话。核对 invocation → 平台投递/实际 turn → next → 原生任务 handle，不只看脚本 wake 或 agents 目录。

只读检测脚本与被唤醒后的主级执行指令必须分开：探针不next，但有ready消息的主级处理入口必须next并创建独立执行者。若唯一的wake处理任务被设置成“只读、不领取”，即使delivery.surface=main也没有证明自动处理已接入，详见[AUTOMATIC_DISPATCH.md](AUTOMATIC_DISPATCH.md)。旧串行者已退出时，先由当前真实主级运行核对台账并接管实际ready，再验证后续无人操作的自动唤醒，不凭空宣称仍有兜底。

主代理空闲时可等待真实平台 wake；不能在主循环同步 curl、等上传、等单个子任务完成。短问答由各自任务直接回微信。微信回复使用纯文本、无 Markdown，只发真实结果，不加“收到，正在处理”等占位内容，普通问候同样如此。仅在已有实质阶段结果或已核实失败/阻塞时，才用稳定 ID 发 progress 并控制频率；不把领取或开始执行当作结果，不编造预计耗时。有后台工作时 next 用短等待，以便续租、处理回执和新任务。只有有证据的资源限制、任务依赖或上游限流才暂缓派发，并保留原因。

## 刷新后的恢复顺序

以下是主代理的恢复流程，不是可自动执行的平台注册 API。必须把该流程接入实际存在且经验证的刷新后启动入口；入口不存在或 hook 仍不能触达主代理时，如实标记“自动恢复未接入”。

1. **先读状态**：核对当前实例/刷新时间、项目和配置路径、SQLite 是否存在、状态锁、实际 daemon 与原生任务状态。旧目录/PID 文件不是进程存活证据，PID 也可能复用。已有健康桥时不重复启动，不重新扫码。脚本若需从备份恢复，保留真实平台输出适配。
2. **恢复唯一桥服务**：若确认原进程已停止且平台服务管理器仍可用，恢复原有服务注册、配置与代理环境后启动一次。若 systemd 已不可用，应使用平台真实提供的进程/启动管理入口，不能只因为有 systemctl 命令就认定存在 manager。CLI/daemon 版本分别核对；服务恢复后检查登录与至少一次轮询成功。
3. **对账未完成事件**：读取原始私密交接文件，查询对应原生 handle。只有平台确认旧任务已停止/终止后，才由主代理为该事件指定一个恢复执行者。创建结果未知先查询，不再创建一份；刷新后不要一律重派所有历史任务。
4. **接续原租约**：原 token 完整且仍有效时，使用原 token 正常 renew 后接续，不必机械等待 30 分钟；同一事件只有一个实际执行者。缺少原 token 时只能等待当前租约到期后正常领取，不能抄数据库 token、强制释放或修改截止。已 accepted 的最终回复只核对，不再发。
5. **核实外部效果**：刷新杀死本地进程，并不能撤销已提交到远端的生图、付款、部署等动作。started/unknown 或仍在远端执行的工具先查真实结果，不换 ID 重跑。原 lease 的工具正常结束可写 completed，包括已核实的失败结果；换租约或结果未知时须真实核对后 --reviewed，不能只为解除回复拦截打标。
6. **恢复主级调度**：核对已接管事件，恢复新事件领取与原生派发、每事件正常续租、异步回执检查。不要启动一个无限替死亡 worker renew 的 shell 来掩盖停滞。仅调度者轮换时，仍活跃的独立执行者继续负责原事件，不重复接管。
7. **恢复观测并复验**：为本次观测使用新 UTC 时间戳的报告路径，保留旧段和重启缺口。自动发送任务只能来自真实待处理事件；从手机发一条编号测试，主聊天不人工介入，核对实际自动领取、回复和手机显示。手动恢复不能记作自动恢复通过。

桥 SQLite 备份不包含 worker 私密交接目录、工具账本、平台 hook 注册或原生任务状态；这些按各自的私密持久化/备份方案保留。观察器72小时记录跨刷新时，逐段标明开始/结束/缺口和恢复耗时，不能把不连续段拼成“无中断连续通过”。

## 告警、claim 和工具的处理

- `worker_claim_gap`/backlog：有 ready 消息却缺领取进展。全部已领取、ready=0 时不会触发 claim_gap，应查看 lease_stalled/步骤/发送诊断。先查主级调度及实际投递，不靠增加执行线程或缩短轮询掩盖无人领取。
- `worker_lease_stalled`：未完成有效租约超过默认10分钟无领取/续租/checkpoint 活动；不是微信网络错误，也不是进程死亡证明。核对旧任务、原始交接和外部操作后再交接。有效租约保护旧所有者，不能为了快而清除。
- `task_step_uncertain`/started：超时只能标为需核对并停止新增副作用，不能自动改 completed 或跳过 reviewed。先查原工具和远端结果；已确认失败的无副作用查询可记真实失败并结清，未知外部效果须核对后再处理。已核实的具体阻塞可发稳定 progress，不提交虚假成功或先 ack。普通问候和无副作用短查询无需为了“安全”全部写 started。
- hook/探针只读 health/diagnose，不 next、不 rm -rf claim 目录。实际领取使用 rc.7 --output-dir；它只移除本次确认空响应。老空目录先独立清点，再核对归属逐个维护；旧的 awaiting_response、不完整或非空文件都是待核对证据，不能批删。
- 新 hook 告警 reason 带 UTC 检测时间，具体代码与脱敏样本在 ~/.cache/muse-link/hook-alert-state.json。收到任何 wake 后先复查当前 status/health，必要时 diagnose；若旧告警已过时且当前健康、无待办，静默结清，不据旧告警重启或重复告警。现有平台 wrapper 被保留时，须明确合并新检测器并 dry_run，不能仅凭升级代码就声称探针已更新。

## 外部 API 超时

外部任务只使用本事件私密原始指令中的目标与凭据，不从公开示例或旧事件复制。调度者不等待网络诊断，其他独立消息继续派发。

只读查询限制次数与整段截止；未知远端副作用先查原任务或幂等键，不重复提交。暂停任务不因升级、换班或恢复而自动获得重测授权。不得更换未授权主机或向其转发凭据。

源站 Authorization 头通常在 TLS 建立后发送，不能凭超时推断代理按该头阻断 TLS。必要的授权诊断只记录无敏感内容的阶段耗时与状态，不公开含请求头的 trace。桥数据库不是通用外部 API 审计账本，缺记录不能证明调用从未发生。
