请由 Meta Muse 主代理为当前 v0.4.0-rc.5 部署接入环境刷新后的恢复。

目标：主聊天登记平台巡检，巡检检测异常后经正式入口自动通知原主聊天，由主聊天查询并重建 worker；环境刷新后也须另行实测。使用当前已确认的 worker 数量及处理模式，仅补缺失者，不调整并发方案。

本指令仅适用于 rc.5。使用已安装 rc.5 的 docs/MUSE.md、docs/PRODUCTION.md、docs/BURST_MESSAGES.md 和 deploy/muse-link.service.in。保持现有程序和数据库，不升级、不清库、不重放已完成任务、不推送仓库。

一、分别验证主聊天权限与定时通知链路

1. 使用 Muse 平台实际提供的独立定时任务能力，安排一次只读验证。该次运行必须由调度器实际触发；主聊天里手动运行不算通过。
2. 使用平台正式支持的投递/回调入口，将定时验证通知自动送达原主聊天，由该主聊天调用原生工具查询台账中的真实 worker handle。记录注册标识、定时触发/实际投递/主聊天执行 UTC、运行身份与查询结果。未发现正式入口时记通知链路未接入，不虚构工具参数，不以 hook 输出 wake 代替送达证据。
   台账缺完整 handle 时由主代理先原生核实后私密补全。按创建时间、父代理或平台数据库推断不能替代原生查询。独立巡检只能查自己的 direct 子任务时，应记 unknown、不自行补位，由接到通知的主聊天核实；不能据此认定主聊天也没有权限。
3. 主聊天创建 worker 的权限另行记录。必要且已授权时，可用一个不领取微信、不调用外部 API、只返回固定标记的短原生任务验证。独立巡检能创建自己的短任务，只证明它本身的权限，不能代替自动送达主聊天的验证。另选巡检直接补位路线时，才需验证该运行同时能查询原 worker 并创建接班者。
4. 核实定时注册属于平台调度服务，是否保留在 Linux 运行环境之外；确认运行互斥或平台排队语义，避免两次恢复同时创建消费者。
5. 只有 Linux crontab、shell 或普通子任务检测，没有正式且已验证的主聊天自动投递入口时，不能算 worker 自动恢复接入；保留检测并准确报告链路缺项。

二、将恢复所需资料持久化到 HOME

1. 私密保存实际安装位置、配置位置、状态目录、rc.5 服务模板、worker 完整指令、当前各 slot 的真实 handle，以及原始事件交接与后台工具账本。目录 0700，文件 0600。
2. worker 指令必须规定：每条完成立即再次 next；空队列继续长轮询；阶段报告提交后继续值守；真实工具和租约按 rc.5 原协议维护。
3. 保存维护开关，主动停服、人工接班前启用；巡检看到维护状态时不启动替代者。
4. 桥 SQLite、worker 私密交接、后台工具记录分别保存。登录凭据或关键交接已丢失时，准确报告并等待必要的人工核对，不伪造登录或工具完成状态。

三、权限验证通过后，更新已有平台独立巡检

巡检负责只读检测和正式平台通知，原主聊天收到自动通知后主动执行以下核实与恢复，不等用户转述；通知链路未验证时不能冒称接通，也不把未验证的 hook wake 当作可靠入口。主聊天按稳定故障合并巡检通知与 worker 结束回调，避免两条入口各建消费者。默认每 3 分钟，已有每 15 分钟巡检时更新原注册，不重复新建，回读间隔、启用状态和下一次触发。检查有界，上轮未完不并行恢复；恢复延迟还包括平台投递和原生任务启动，需实际记录，不能保证一个巡检周期内恢复。

A. 只读判断

1. 读取维护开关、恢复台账、上次未决创建请求和当前平台原生任务状态。
2. 查询保存的真实 handle，并检查是否已有接班者。running、starting、等待授权时保留原消费者；不能仅凭 10 分钟没有领取、health=503、空闲或旧心跳认定任务已死亡。
3. 平台查询超时、结果不完整、旧 handle 查不到但没有终止证明、存在多个可疑活跃者时，记录 unknown 并停止新建。恢复意图或创建结果不明时先核对原请求，不换标识重复创建。

B. 恢复桥服务

1. 先检查实际进程、监听端口、服务管理器与配置。已有健康桥时继续使用，不重复启动或重启。
2. HOME 下安装完整、Node.js 24+ 及 systemd 可用，而 /etc/systemd/system/muse-link.service 已丢失时，通过下述统一入口在同一锁内调用 repair-service.sh 的 --check/--apply。内层只渲染并重建缺失单元、daemon-reload；外层负责核对授权及后续启动，不重装、不改配置/登录/数据库；已有不同单元会拒绝覆盖。完整说明见 rc.5 docs/RUNTIME_RECOVERY.md。
3. 服务存在且只是停止时，按已授权的意外停止恢复策略启动一次；统一使用公开安装包的 deploy/recover-service.sh，不在巡检中分步 enable/start。按 docs/RUNTIME_RECOVERY.md 核对 ~/.config/muse-link/recovery.json（0600）：auto_start 默认 false，仅按已有授权改为 true；维护时 maintenance=true。外层脚本同一 flock 覆盖补单元、启动和结果保存，失败持久化退避，未决 pending 不盲目重试。不要为单元丢失重新跑安装、init 或登录。
4. 恢复入口：

   bash "$HOME/.local/share/muse-link/current/deploy/recover-service.sh" --check
   bash "$HOME/.local/share/muse-link/current/deploy/recover-service.sh" --apply

   第二条仅在已有恢复授权下运行。独立补充包可用其真实绝对路径，不切换 current。退出码见 docs/RUNTIME_RECOVERY.md；内部 Node 入口不要绕过 bash 持锁入口直接调用。自定义配置/服务先适配核验。

   复查使用实际 CLI 绝对路径：

   systemctl is-active muse-link
   "$HOME/.local/bin/muse-link" status
   "$HOME/.local/bin/muse-link" health

5. 核对后台 version=0.4.0-rc.5、logged_in=true、至少一轮轮询成功。刚启动尚未产生轮询结果时有界等待；worker_backlog 按积压处理，不能因为该告警永远不恢复消费。
6. Node、程序文件、systemd 管理器或有效登录缺失时，报告具体缺项。需要用户重新扫码时暂停相关操作，不每分钟重复创建二维码。

C. 恢复真实 worker

1. 仅在平台明确确认旧 worker 已终止、当前对应 slot 没有活跃替代者时补位。其它健康 slot 保留。
2. 在创建前，持久化一个稳定恢复标识、原 handle、slot、原交接位置和本次尝试状态；确保该流程互斥。使用真实平台任务工具创建接班者，指令包含稳定恢复标识，保存返回 handle 并核实其实际状态。
3. 创建调用超时或回执不明时，保留同一恢复意图，先查询平台实际任务；无法排除已经创建时不再 spawn。文件存在或进程目录存在不能代替平台查询。
4. 接班者先对账原事件及后台工具。旧执行者已确认终止、原交接 token 完整且仍有效时，通过正常 renew 后续接；token 已丢失或失效时等待合法重新领取。不从数据库抄 token、不清有效租约。
5. started、unknown 和远端仍在执行的工具先核实实际结果。已 accepted 的最终回复不重发，不用重新跑外部任务来验证恢复。
6. 确认新 handle 进入持续 next/reply 循环后记录恢复完成。仅 spawn 成功、health 全绿或队列暂时为空不能作为持续值守证据。
7. 恢复失败退避，15 分钟内最多 3 次创建尝试；未决创建保留原关联，不换标识绕过。主聊天仅在状态发生实质变化、需要扫码或人工核对时通知，健康时静默。

D. 巡检与持续值守补充

1. 使用 node "$HOME/.local/share/muse-link/current/scripts/runtime-check.mjs" --config "$HOME/.config/muse-link/config.json" --job-dir "$HOME/.local/state/muse-link-worker/jobs" 读取桥与工具状态。该检查不获取桥状态锁；后台工具 list/pending 报 state_locked 不能当作正常，应保留具体调用与错误并核对入口。
2. 最近领取只是活动证据，真实 worker 状态必须由平台原生任务查询。旧的“15 分钟无活动就创建”规则应替换，不重复注册第二个巡检。更新原计划为每 3 分钟，但调度、轮询与启动还有额外延迟，不能承诺最长 3 分钟内恢复。
3. 阶段报告只私密追加，不以终结任务的 final 报告退出。健康巡检静默；故障首次出现、实质变化、恢复或需用户操作才通知。上下文边界或实际终止时，先保存交接，再由有权限的调度者确认旧者结束后补位。
4. 长工具按 BURST_MESSAGES.md 后台启动后继续 next；有工具/媒体/发送待办时 wait 不超过 5 秒，空闲恢复 30 秒。逐轮检查结果和续租，普通只读 HTTP 默认连接 10 秒、总计 60 秒、不自动重试，包装须传递 curl/HTTP 失败。向现有真实 worker 追加后取得私密回认并核对实际领取，未生效不标通过。
5. 用户级 systemd 先只读核查 user manager、D-Bus、linger 与刷新触发条件；单元在 HOME 不保证管理器会自启，未验证不切换当前健康服务、不启第二个桥。HOME 中修复脚本存在不代表刷新后自动执行，之前 HOME 留存也不能替代私密备份。

四、分别验收两种恢复，不混算

1. worker 补位验收：在没有未决副作用的受控窗口，保存交接并正常结束一个测试消费者，保留巡检。用户不在主聊天输入恢复指令，只从微信发编号消息；主聊天经平台自动触发后的核实与恢复是验收链路的一部分。记录巡检触发、通知送达、主聊天执行、新真实 handle、实际领取、最终 accepted 和手机收到时间。用户手动救援则不算自动通过，不能只因执行者是主聊天就认定人工。
2. 环境刷新验收：需另行确认受控窗口后执行。刷新前保留全部交接，刷新后用户不进入主聊天输入恢复指令，只发微信消息。核对平台定时注册是否保留、巡检是否实际执行并自动通知主聊天、服务单元是否重建、worker 是否自动补位，以及微信结果。
3. 主动维护不补位、运行中和等待授权不重复创建、创建回执不明不重复创建也需检查。
4. 未实际做环境刷新，就将“刷新后自动恢复”标为未执行；不能因为 worker 补位通过而宣布环境刷新恢复也通过。

五、最终回传

请分别报告：
- 平台定时任务：真实注册标识、实际触发与主聊天投递时间；主聊天原生查询/创建权限和自动投递验证分别报告。
- 桥恢复：现有安装能否重建服务单元，登录及轮询检查结果。
- worker 补位：原 handle 的终止证明、新 handle、进入持续循环的证据。
- 环境刷新：通过／失败／未执行，真实故障与恢复耗时。
- 未接入项：无正式主聊天自动投递入口、投递未证实、主聊天无法核实原 worker，或刷新后巡检不运行时，分别报告链路缺口，不声称全自动恢复已经实现。

报告只回传脱敏状态与必要标识；不输出凭据、token、消息正文或私密交接内容。
